## What is this project?

Electricity theft — also called **non-technical loss** — includes meter bypass, tampering, line tapping, and billing fraud. Detecting it from smart-meter readings normally means collecting household-level consumption records in one central server. That creates privacy risk and a high-value data target.

**PowerShield-FL** asks:

> Can a lightweight, privacy-preserving, communication-efficient Federated Learning framework detect electricity theft effectively while reducing computational and communication overhead and handling heterogeneous client data?

The project compares three tracks on the same held-out consumers:

| Track | Method | Purpose |
|---|---|---|
| **A. Centralized ML** | Logistic Regression, Random Forest, MLP, Lightweight MLP, CNN-LSTM | Pooled-data performance reference |
| **B. Standard FedAvg** | Same lightweight model, sample-count aggregation, no privacy/compression | Federated baseline |
| **C. PowerShield-FL** | Lightweight MLP + clipping/Gaussian noise + int8 quantization + adaptive aggregation + explainability | Proposed framework |

The implementation covers the complete research pipeline: synthetic/real-data loaders, leakage-safe preprocessing, non-IID client simulation, local training, privacy, communication measurement, adaptive aggregation, threshold tuning, detection, explainability, a Streamlit dashboard, automated report generation, tests, and notebooks.

## Why this project?

- **Privacy:** raw consumption windows never leave a client. Only model deltas and aggregate statistics are transmitted.
- **Communication:** federated updates are large; the project measures and reduces the actual serialized bytes.
- **Heterogeneity:** clients differ in data quantity and theft ratio, so sample-count-only FedAvg may be inappropriate.
- **Lightweight deployment:** the local model has **10,689 parameters** and runs on a CPU.
- **Explainability:** a theft alert should be accompanied by model-derived evidence, not only a probability.
- **Honest research:** unrun experiments are marked `NOT RUN`; synthetic data is labelled; no significance claim is made from one seed.

### Final quick result at a glance

| Method | F1 | Precision | Recall | ROC-AUC | Bytes | Time |
|---|---:|---:|---:|---:|---:|---:|
| FedAvg | 0.9938 | 1.0000 | 0.9877 | 0.9973 | 3,453,520 | 15.51 s |
| **PowerShield-FL** | **0.9969** | **1.0000** | **0.9938** | **0.9969** | **902,449** | **15.97 s** |

**Measured communication reduction: 73.87%** — from actual serialized payloads, including headers and quantization metadata. These are single-seed synthetic results; the F1 difference is descriptive, not statistically significant.

## What we use and why

| Layer | Technology / method | Why this choice |
|---|---|---|
| Language | **Python 3.10+** | Readable research code and the required ML ecosystem |
| Deep learning | **PyTorch (CPU)** | Flexible model control, deterministic local training, no GPU requirement |
| Federated simulation | **Custom simulator** (not Flower) | Full control over exact client updates, byte accounting, privacy order, and reproducible CPU runs |
| Local model | **Lightweight MLP** (133 → 64 → 32 → 1) | 10,689 parameters; fast on a laptop; fair architecture for FedAvg vs proposed |
| Centralized baselines | **scikit-learn** LR/RF/MLP + PyTorch MLP/CNN-LSTM | Standard reference models and a heavier sequence baseline |
| Data | **Synthetic generator** by default; SGCC / long-CSV loaders supported | No real data can be bundled; the synthetic path exercises the whole pipeline honestly |
| Preprocessing | Consumer-level split → cleaning → train-fitted IQR/scaler → 14-day windows | Prevents consumer leakage and preserves theft anomalies by clipping, not dropping |
| Privacy | **L2 clipping + Gaussian noise** | Bounds update sensitivity and adds plausible deniability to client updates |
| Secure aggregation | **Simulated additive masks** (optional) | Demonstrates the interface without claiming production cryptography |
| Communication | **Dense int8 quantization** by default; top-k and top-k+int8 measured | Quantization preserved utility in the sweep while reducing measured bytes |
| Aggregation | **Adaptive size × quality × reliability × class balance** | Handles non-IID clients and avoids collapsing all-normal clients to the minimum weight |
| Detection | Validation-tuned threshold, frozen for test | Prevents test-set tuning and false optimism |
| Explainability | **SHAP KernelExplainer**, permutation importance, gradient×input | Model-derived global and local explanations |
| Dashboard | **Streamlit** | Fast local UI over real result artifacts; honest `NOT RUN` states |
| Tests | **pytest** | Privacy contract, leakage, partition coverage, aggregation, compression, end-to-end checks |

### Why no Flower?

Flower is useful for distributed production deployments, but this project needs a deterministic, CPU-only, inspectable research loop where every serialized byte and every `ClientUpdate` can be measured and tested. The custom simulator provides that. The transport layer could be replaced with Flower/gRPC later without changing the model or evaluation logic.

### Why dense int8 instead of top-k?

Both are measured in the communication sweep. On this dataset and four-round setup, dense int8 quantization preserved validation/test F1 while top-k reduced utility. The project reports that measured result rather than assuming sparsification always helps. Top-k remains implemented and configurable.

## Architecture

```text
Raw data (synthetic or real loader)
        ↓
Consumer-level split FIRST: train / validation / test
        ↓
Cleaning → train-fitted imputation, IQR clipping, scaling → 133 window features
        ↓
Non-IID client simulation (raw windows stay local)
        ↓
Local LightweightMLP training → ClientUpdate (delta + aggregate stats only)
        ↓
Privacy: L2 clip → Gaussian noise → optional simulated secure aggregation
        ↓
Communication: compress + measure actual serialized bytes
        ↓
Server: FedAvg or adaptive aggregation
        ↓
Global model → validation-tuned threshold → test evaluation
        ↓
SHAP / permutation / gradient×input explanations
        ↓
Streamlit dashboard + tables + figures + report
```

Privacy boundary:

```text
CLIENT SIDE                              SERVER SIDE
────────────────────────────────────────────────────
Raw consumption windows                  NEVER received
Consumer identifiers                     NEVER received
Timestamps                               NEVER received
                                         ─────────────
ClientUpdate:                            Received:
  state_dict (model delta)               yes
  num_samples                            yes
  train_loss / val_loss                  aggregate scalars
  val_metrics                            aggregate scalars
  num_positive / num_negative            counts
  update_norm                            scalar
```

`ClientUpdate.validate()` rejects unexpected fields, and `tests/test_privacy.py` enforces the contract.

## Data and leakage prevention

### Default: synthetic demo

The quick suite uses **240 consumers × 180 days × 48 half-hourly readings**. The final run produced:

| Statistic | Value |
|---|---:|
| Consumers (train / validation / test) | 156 / 36 / 48 |
| Window samples (train / validation / test) | 8,736 / 2,016 / 2,688 |
| Features | 133 |
| Raw rows | 2,073,600 |
| Raw missing values | 4,244 |
| Raw duplicate rows | 0 |
| Train-window theft ratio | 8.08% |
| Test-window theft ratio | 6.03% |
| Split unit | consumer |

**Leakage protocol**

1. Split consumers into train/validation/test **before** fitting anything.
2. Fit the imputation median, IQR bounds, and scaler on training consumers only.
3. Transform validation/test with those fitted objects.
4. Tune the decision threshold on validation and freeze it for test.
5. Never delete theft anomalies; clip extreme values instead.

### Non-IID clients

The final quick partition uses five clients with different sizes and theft ratios:

| Client | Samples | Consumers | Theft windows | Theft ratio |
|---|---:|---:|---:|---:|
| client_00 | 2,016 | 36 | 346 | 0.1716 |
| client_01 | 3,640 | 65 | 329 | 0.0904 |
| client_02 | 336 | 6 | 18 | 0.0536 |
| client_03 | 2,408 | 43 | 0 | 0.0000 |
| client_04 | 336 | 6 | 13 | 0.0387 |

Quantity skew moves **whole consumers** between clients; it never thins or drops training windows. All **8,736** training windows are assigned exactly once. `client_03` has no theft windows, which exercises the adaptive-quality fallback (neutral quality `0.5` for a single-class local validation split).

### Real data

Supported loaders:

- **SGCC:** `data.csv` + `label.csv` under `data/raw/`.
- **Long CSV:** `timestamp`, `consumer_id`, `consumption` plus a label source.
- **Generic wide CSV:** consumer ID, date/time, consumption columns, and a theft flag.

No real dataset is bundled or downloaded. If it is absent, the project reports `SYNTHETIC DEMO DATA` and the dashboard keeps that warning visible.

## Quick start

### 1. Install

```bash
cd B:\surya-11
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Tested on **Python 3.14.5 / Windows 11 / CPU only**. Python 3.10+ is required. No GPU or API key is needed.

### 2. Run the fast demo

```bash
python main.py --demo
```

This is a 3-round smoke test with 180 synthetic consumers and 4 clients. It overwrites `results/`; re-run quick mode afterward before quoting the final comparison tables.

### 3. Run the authoritative quick suite

```bash
python main.py --mode quick --seed 42
```

This executes centralized baselines, FedAvg, PowerShield-FL, privacy/communication/scalability sweeps, explainability, tables, figures, and the report.

### 4. Run the dashboard

```bash
streamlit run dashboard/app.py
```

Open `http://localhost:8501`.

### 5. Run the checks

```bash
python -m pytest tests -q
python scripts/run_all_checks.py
```

## Dashboard

The Streamlit app has ten tabs:

1. **Overview** — headline metrics and communication reduction.
2. **Dataset** — source badge, class distribution, cleaning report.
3. **Federated Clients** — client sizes, theft ratios, heterogeneity.
4. **Training** — round history, loss, validation F1, measured bytes.
5. **Model Comparison** — detection, time, memory, parameters, communication.
6. **Privacy** — clipping/noise settings, epsilon estimate, sweep.
7. **Communication** — compression sweep and byte comparison.
8. **Detection** — held-out window explorer with model-derived factors.
9. **Explainability** — SHAP summary, permutation importance, local explanations.
10. **Report** — generated Markdown report and tables.

Honest empty states:

- No summary → **“No experimental result available. Run the experiment first.”**
- Missing/corrupt checkpoint → an error, never a fabricated prediction.
- Missing sweep → `NOT RUN`.
- Synthetic data → a permanent `SYNTHETIC DEMO DATA` warning.

The dashboard was validated with Streamlit `AppTest` (10 tabs, no exceptions) and a live headless health check on port `8511` (`HTTP 200`, body `ok`).

## Limitations and honest non-claims

1. **Synthetic data only** in the executed results; no real utility dataset is bundled.
2. **Single seed** in the quick suite; no statistical significance is claimed.
3. **Full mode is configured but NOT RUN** (600 consumers, 10 clients, 25 rounds, 3 seeds, up to 20 clients).
4. **Real SGCC/IRISE execution is `DATASET NOT CONFIGURED`**.
5. **Epsilon is a single-release estimate**, not end-to-end differential privacy; composition across rounds is not implemented.
6. **Secure aggregation is simulated additive masking**, not cryptographic secure aggregation.
7. **Clients are simulated**, not a real distributed deployment.
8. **Timing and memory are machine-specific** and not portable benchmarks.
9. **Top-k lost utility in this setup**; dense int8 is the measured default, not a universal claim.
10. **The demo is a smoke test**, not the final experiment; it overwrites `results/`.

Full details: [`FINAL_STATUS.md`](FINAL_STATUS.md) and [`docs/evaluation.md`](docs/evaluation.md).

## Reproducibility

All randomness flows through `utilities.seed.set_seed` / `make_rng`. The final quick suite is:

```text
experiment_20261025_014623_793809_suite_s42
```

Re-run:

```bash
python main.py --mode quick --seed 42
```

Every run writes `config.json`, `metrics.json`, `metrics.csv`, `logs.txt`, checkpoints, and predictions under `results/raw/<run_id>/`. The report generator reads `results/metrics/summary.json`; it does not accept manually typed metrics.
